# Security and documentation audit — `liraan/pcfootballmanager`

**Audited revision:** `b6d8a6dba83c04d71abc0887e7d8538199e15a0c` (`origin/main`, 2026-10-30).
**Scope:** Current Rust source for Plane A data flow, event/save/demo serialization, path input, unsafe/deserialization/network/process APIs, dependency lockfile, and selected specifications, architecture documents, ADR-003, and current session state. Comparison with the prior audit commit `943b3178db1c384879c77fd51cd76ccb105afc23` found 14 later commits, all affecting documentation; no Rust source changes were present in that range.
**Method:** Read-only source/document inspection and targeted text searches. No files outside this report were changed.

## 1. Executive summary

The previously reported Plane A data exposure remains present in the current code. Hidden values are copied into serializable cause factors, then into match events, save files, and the demo's JSON output. This is a local information disclosure in the inspected application; no remote endpoint or cross-user exfiltration path was identified.

The review also found documentation drift: architecture and tour pages present attempt/outcome event linkage as implemented, the documented save contract differs from the code, and ADR-003 still contains obsolete `pcfm-debug` references despite a later rename note. Additional deterministic-behavior and panic-handling discrepancies are recorded below.

## 2. Security finding

| # | Severity | File | Lines | Vulnerability | Confidence |
|---|----------|------|-------|---------------|------------|
| 1 | 🟡 MEDIUM | `crates/pcfm-hidden/src/lib.rs` | 140–145, 182, 213, 262 | Latent player values enter serializable `Factor.value`, then events, save JSON, and demo JSON output. | 9/10 |

### R-01 — Latent values exposed through event and JSON/save surfaces

`pcfm-hidden` writes `attacker_score` and `defender_score` into factors at `crates/pcfm-hidden/src/lib.rs:140–145`, `shooter.finishing` at `:182`, `passer.passing` at `:213`, and `player.injury_proneness` at `:262`. These are read from private latent state. The public `Factor` has `name` and `value` and derives `Serialize` (`crates/pcfm-model/src/cause.rs:11–16`); `MatchEvent` also derives `Serialize` and contains `cause_trace` (`crates/pcfm-stats/src/event.rs:84–109`). The match engine forwards causes into events (`crates/pcfm-match/src/state.rs:111–143,265–278`).

The result is externally readable from the demo's `--json` output (`crates/pcfm-demo/src/render.rs:60–62`) and from save serialization (`crates/pcfm-match/src/save.rs:130–143`). This contradicts the observed-only cause rule in `specs/L0-match/05-match-events.md:117–124` and the stated Plane A boundary in `specs/L0-match/10-ground-truth.md:96,102,108–118`.

**Impact and limits:** This exposes hidden game attributes to anyone who can inspect the local output or save and could provide an unfair gameplay advantage. The reviewed source did not establish a remote network input/output path, so remote exploitation or cross-user disclosure is not claimed.

## 3. Other security checks and limits

- **Secrets:** targeted source searches found no hard-coded credential candidates in the Rust code inspected. This was a pattern search, not secret scanning of every historical revision or binary.
- **Unsafe code:** no `unsafe` blocks were found in the inspected Rust sources; the root manifest denies unsafe code (`Cargo.toml:47`).
- **Network and process execution:** no socket APIs or external process invocation were identified in the inspected Rust source. The demo's `std::process::ExitCode` is not process execution (`crates/pcfm-demo/src/main.rs:10–15`).
- **Deserialization:** save loading uses `serde_json::from_slice` (`crates/pcfm-match/src/save.rs:142–143`); no custom or unsafe deserializer or remotely reachable decode path was established.
- **Filesystem paths:** `--html <PATH>` accepts a caller-supplied local path (`crates/pcfm-demo/src/main.rs:74–77`) and writes HTML there (`crates/pcfm-demo/src/render.rs:88,159`). This is the documented local output feature; no remote control of the path was found, so it is not classified as a vulnerability.
- **Dependencies:** `Cargo.lock` pins the registry dependencies. No `cargo audit` or `cargo deny` advisory check was run, so known-CVE status is unknown. The lockfile inventory is not an advisory scan.
- **Tests:** no build or test command was executed in this audit. `docs/context/SESSION-STATE.md:43` records a previous green baseline (build, clippy, 103/103 tests, fmt, test-runner 6/6); that historical record is not a result from this audit.

## 4. Documentation and specification inconsistencies

### R-02 — Attempt/outcome event model documented as implemented

`docs/ARCHITECTURE.md:124` and `docs/CODE_TOUR.md:143` state that the engine emits attempt events with `PositionSnapshot`, followed by outcomes linked by `attempt_event_id`. The L0 event spec defines these at `specs/L0-match/05-match-events.md:64–68,145–160`. The current `EventType` and `MatchEvent` lack attempt variants and linkage fields (`crates/pcfm-stats/src/event.rs:23–64,85–115`), while the engine emits `Shot` and `Goal` directly (`crates/pcfm-match/src/state.rs:111–143`). The docs should label that behavior as target/planned rather than current.

### R-03 — Save specification differs from implementation

`specs/L0-match/07-save-minimal.md:60–71,132–144` specifies a `command_log`, `SemVer` configuration versions, and postcard serialization. The implementation's `MatchSave` contains no `command_log` and stores string versions (`crates/pcfm-match/src/save.rs:80–98`), initializes `config_versions` empty (`:112–119`), uses JSON (`:130–143`), and replays with `MatchConfig::default()` (`:187–191`). The save contract should clearly distinguish current implementation from target design.

### R-04 — ADR-003 retains stale crate references

`docs/adr/003-plane-a-enforcement.md:206` contains a note that ADR-020 renamed `pcfm-debug` to `pcfm-test-runner` and split out `pcfm-demo`. The subsequent section still describes `pcfm-debug` and references paths under `crates/pcfm-debug` (`:208–237`). The workspace instead lists `pcfm-test-runner` and `pcfm-demo` (`Cargo.toml:5–15`).

### R-05 — Repository inventory and SIM_VERSION location prose are stale

`STRUCTURE.md:101–113` says the ADR directory has 17 files numbered 000–019; the current directory contains the template and ADRs 001–008 and 012–022 (20 files). `STRUCTURE.md:340–360` already includes ADRs 020–022 and lists 18 accepted decisions. Separately, `CHANGELOG-SIM.md:19,41` says `SIM_VERSION` is planned in `pcfm-core`; the constant is currently in `crates/pcfm-match/src/save.rs:76`.

### R-06 — Plane A boundary and API prose contradict implementation

`docs/ARCHITECTURE.md:90–92` and `docs/CODE_TOUR.md:90,113` describe `ObservationEvent`/`resolve_*` as the sole output boundary and claim the engine never sees latent values. Those claims do not account for the `CauseTrace` disclosure in R-01. Additionally, `specs/L0-match/10-ground-truth.md:75,106–111` specifies a restricted public API and a `GroundTruth { .. }` Debug form, but implementation provides `world_seed()` and `match_id()` (`crates/pcfm-hidden/src/lib.rs:84–91`) and Debug prints these non-latent fields (`:351–356`).

### R-07 — MatchContext reference count is inaccurate

`docs/CODE_TOUR.md:128` describes `MatchContext` as having “5 references.” Its implementation has four references (`match_`, `hidden`, `rng`, `chain`) and a by-value `MatchConfig` (`crates/pcfm-match/src/context.rs:47–57`).

## 5. Determinism and runtime behavior observations

### R-08 — Match RNG stream names omit match ID

`specs/L0-match/01-rng.md:64–78` requires match-scoped stream names; the implementation uses fixed names `match:actions`, `match:action_kind`, and `match:player_pick` (`crates/pcfm-match/src/state.rs:57–63`). The registry derives a stream from the world seed and stream name (`crates/pcfm-core/src/rng.rs:87–91`). Thus, matches sharing a world seed begin these engine streams identically, contrary to the specified per-match isolation.

### R-09 — Player picker uses one random roll for both players

`crates/pcfm-match/src/state.rs:217–229` uses the same `roll` to select attacker and defender indices. For equal-sized squads, the selected relative indices always match, coupling each attacker with the same slot on the opposing side. This is a concrete selection bias; the source describes the engine as a prototype (`state.rs:70–76`).

### R-10 — EventBus handler panics propagate

`specs/L0-match/02-event-bus.md:108,129` says handler panics are caught/logged and the match continues. The implementation documents propagation and loss of drained events (`crates/pcfm-core/src/event_bus.rs:81–85`) and invokes handlers without a panic boundary (`:126–140`).

### R-11 — `expect` calls remain in simulation paths

`docs/context/NEW-SESSION-PROMPT.md:86` prohibits `unwrap`/`expect`/`panic!` in simulation paths. `crates/pcfm-match/src/state.rs:57–63` and `crates/pcfm-hidden/src/lib.rs:68–71` use `expect` to construct stream names. The current names are literals or formatted with a fixed non-empty prefix, so an input-triggerable panic was not established; these remain policy violations.
