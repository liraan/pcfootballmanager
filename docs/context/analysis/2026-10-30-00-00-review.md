# Repository audit — `liraan/pcfootballmanager`

Note: this analysis was prepared from the repository state and the latest prior audit records already in `docs/context/analysis/`. I did not re-run the cargo toolchain in this session because the terminal runtime is not available in this chat; the figures below are therefore the last verified values in-repo and should be re-confirmed before any release decision.

## 1. Executive summary

The project remains internally coherent and structurally consistent with the Three Planes doctrine. The canonical doctrine states that Plane A is ground truth, Plane B is observed data, and Plane C is estimation, and the implementation follows that pattern in the workspace layout and crate boundaries (`modules/00-foundations.md:51-131`, `docs/ARCHITECTURE.md:73-92`, `Cargo.toml:3-15`).

The most recent repository audit recorded the following real verification results from the local toolchain: `cargo build --release` passed, `cargo test --workspace` reported 103 passed / 0 failed, and `cargo clippy --workspace -- -D warnings` reported zero warnings (`docs/context/analysis/2026-10-29-18-18-review.md:25-36`). Those results are consistent with the repo’s architecture and the crate graph described in `docs/ARCHITECTURE.md:19-68`.

The remaining concerns are documentation drift and a few non-blocking operational cautions rather than a security incident or a broken core engine. The key caveat is that the audit output should be refreshed before a release if the codebase has changed since the last audit snapshot.

## 3. Security static scan

The repository remains free of the high-risk patterns expected in a prototype engine:
- no hardcoded credentials or tokens were found in the current workspace state
- no `unsafe` blocks were reported in the workspace lint configuration (`Cargo.toml:46-58`)
- no `std::net` usage was identified in the relevant runtime crates
- no shell execution via `std::process::Command` was identified in the inspected Rust sources
- no unsafe deserialization pattern was identified (`docs/context/analysis/2026-10-29-18-18-review.md:65-82`)

The single notable security-adjacent issue from the prior report was a CLI path-safety concern in the demo HTML writer: `pcfm-demo` accepts `--html <PATH>` and writes the rendered file to the provided path (`crates/pcfm-demo/src/main.rs:75-88`, `crates/pcfm-demo/src/render.rs`), which should be treated as a local file-creation vector and ideally sanitized before production use (`docs/context/analysis/2026-10-29-18-18-review.md:75-78`). This is not a critical vulnerability in the current scope, but it is the one relevant path traversal risk documented in the repo history.

## 4. Coherence: spec ↔ code

The architecture and doctrine are explicitly aligned with the code structure:
- `modules/00-foundations.md:51-131` defines the Three Planes and the ban on latent leakage
- `docs/ARCHITECTURE.md:73-92` says Plane A is `GroundTruth` in `pcfm-hidden`, Plane B is `MatchEvent`/`EventChain` in `pcfm-stats`, and Plane C is not yet implemented
- `Cargo.toml:3-15` and `docs/ARCHITECTURE.md:19-68` show the crate graph: `pcfm-hidden`, `pcfm-stats`, and `pcfm-match` are the key boundary crates

The repo’s design also enforces separation by crate boundaries. The `pcfm-match` crate depends on `pcfm-hidden` and `pcfm-stats`, while `pcfm-stats` does not depend on `pcfm-hidden` according to the architecture description (`docs/ARCHITECTURE.md:19-68`, `docs/ARCHITECTURE.md:84-92`).

The main coherence concern is not logic breakage but drift between the specification and documentation snapshots. Earlier audits explicitly noted that the spec docs sometimes lag behind the implementation, including `CHANGELOG-SIM.md` and ADR references (`docs/context/analysis/2026-10-29-18-18-review.md:54-61`). The repo is coherent enough for L0 work but still requires periodic documentation alignment before release.

## 5. Doctrine: Plane A / B / C

The doctrine is consistent with the code split:
- Plane A is the hidden ground truth: `pcfm-hidden` owns `GroundTruth`, latent data, and the resolution functions (`docs/ARCHITECTURE.md:78-92`, `crates/pcfm-hidden/src/lib.rs`)
- Plane B is observable match outcomes: `pcfm-stats` owns `MatchEvent` and `EventChain` (`docs/ARCHITECTURE.md:78-92`, `crates/pcfm-stats/src/lib.rs`)
- Plane C is intentionally not implemented yet, which matches the project roadmap (“L1–L3 planned” in `docs/context/NEW-SESSION-PROMPT.md:29-43` and `STRUCTURE.md:101-143`)

The core prohibition is explicit: no module should read hidden values directly except the match engine via the resolution path (`modules/00-foundations.md:55-83`, `docs/ARCHITECTURE.md:90-92`). Based on the current repo structure and docs, the repository still appears to honour the separation in design even though the broader L1/L2 stack is not implemented yet.

## 6. Determinism

Determinism is a first-class design target in the doctrine and the crate layout. The project requires named RNG streams and local determinism; this is documented in `modules/00-foundations.md:133-147` and the architecture narrative (`docs/ARCHITECTURE.md:99-135`). The repo uses a deterministic RNG registry pattern and reconstructs state from `(world_seed, match_id)` for save/load behavior (`crates/pcfm-core/src/rng.rs`, `crates/pcfm-match/src/save.rs`).

The earlier audit also noted that no `HashMap`/`HashSet` simulation-path anti-pattern is being used in the current design and that the project’s save strategy preserves deterministic replay semantics (`docs/context/analysis/2026-10-29-18-18-review.md:85-89`). This is consistent with the stated doctrine in `modules/00-foundations.md:133-147`.

The main caveat remains documentation completeness: `SIM_VERSION` and the release notes need to be kept in sync with implementation changes, as noted in the earlier audit (`docs/context/analysis/2026-10-29-18-18-review.md:54-61`).

## 7. Correctness observations

The current project has a few design notes that are worth preserving for future work:
- The simulation is deterministic and renderer-agnostic according to the architecture split in `docs/ARCHITECTURE.md:138-159`.
- The match demo intentionally treats HTML output as a generated artifact, and the CLI can write it to a target path (`crates/pcfm-demo/src/main.rs:92-130`).
- `pcfm-demo` includes explicit tests for rendering and scenario validity (`crates/pcfm-demo/src/main.rs:133-163`).
- The earlier audit specifically called out a non-security issue in `pick_players` correlation and a placeholder model for action probabilities, but marked these as design notes rather than bugs (`docs/context/analysis/2026-10-29-18-18-review.md:85-91`).

The project is still in a prototype stage and should be treated as such: L0 exists and is coherent, but L1–L3 and the broader world model remain planned work (`STRUCTURE.md:101-143`, `docs/context/NEW-SESSION-PROMPT.md:29-43`).

## 8. Verdict and next actions

The repository remains in a healthy state for its current scope. The design doctrine is coherent, the crate boundaries are sensible, and the main risks are documentation drift, the CLI HTML output path issue, and the need for a fresh verification run before any formal release claim.

Recommended next steps:
1. Re-run the cargo toolchain in a shell with the repo checked out locally and confirm the current numbers before release.
2. Sanitize the `--html` file path in the demo binary if the tool is intended for broader use outside local testing.
3. Align any stale docs that mention `SIM_VERSION`, earlier ADR references, or implementation drift.
4. Re-issue the audit report after the fresh command output is captured.

This is a coherent prototype repository, not a production-grade sports-management platform: the architecture is solid, the doctrine is clear, and the operational risk is mostly in stale-doc and verification discipline rather than in the core simulation model itself.
